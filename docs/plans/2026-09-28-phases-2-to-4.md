# Autonomous delivery, Phases 2 to 4: plan

> **Status: accepted** (2026-09-28, revision 3). It continues [the autonomous-delivery plan](2026-09-26-autonomous-delivery.md)
> (D1 to D8 stand) from Phase 1 as built ([status](2026-09-27-finalize-delivery-harness.md)). Decisions
> D9 to D17 signed off by Benjamin on 2026-09-28, all at their proposed defaults.

**End state of the program:** in a repo that enables ship-to-prod, a need stated once goes from the prompt
to **`delivered`** with no human intervention, on GitHub and on GitLab: merged at its reviewed head sha
and, in a repo that deploys, deployed and verified in production by its own acceptance probes. A red
deployment or a red production probe opens a revert PR/MR and escalates. The need survives the death of
its session. Elsewhere, the end state stays `ready`.

| Phase | Adds | End-to-end evidence |
|---|---|---|
| 2 | Acceptance probes: each criterion has a probe, red before the work, green at the shipped head | E2E `needs` space gains acceptance, env-aware and amended-criterion needs |
| 4 | Supervisor: an idle session is woken, a dead one is resumed | hermetic supervisor suite, and one real run where a session is killed mid-need and the need still ends |
| 3 | ship-to-prod: sha-bound merge on an up-to-date branch, deployment watch, production verification, revert | E2E `deliver` space: delivered, deploy red, production red, base drift, on both forges |

Phase 4 comes before Phase 3 (D16): ship-to-prod adds the longest waits (pipelines, deployments), and
the supervisor is what keeps a need from stalling in them.

---

## Starting point: Phase 1 as built

Where the build differs from the 2026-09-26 design, the build is the reference.

- **Stages** (`conductor.py STAGES`): implementing, gating, proving, reviewing, shipping, ci, ready. Each
  answer comes from the owner's read-only `stage` CLI; script steps run inside the Stop hook (120 s
  budget), background steps come back as commands carrying `--need <id>`, skill steps are judgment.
  The conductor re-asks every stage from the first at each Stop.
- **Criteria are free text** and `open` accepts none. Proving checks the bug repros that the need's
  sessions recorded (session-keyed, schema v1).
- **Ledger:** `.git/conductor.json` with a whole-need history (20 entries); `need_holds()` in the kernel
  decides whether a need holds its branch; `reopen` restores a `ready` need from the history. A need is
  bound to a session id; the pid is updated on `compact`, `clear` and `resume`.
- **Re-entry** relies on the task notification of the background step the model launched. Neither the
  `CronCreate` wake-up nor `asyncRewake` was built.
- **Report** at `ready`: the need, its branch and each stage's evidence; no time, no cost, no
  per-criterion evidence.

## Phase 2: acceptance probes

**Deliverable:** proving checks the contract. Every criterion has a probe that failed before the work
and passes at the shipped head, or a recorded, visible reason why not. Probes are keyed by need and
criterion, so adopting or resuming a need carries its evidence.

### 2.1 The contract

- `open` requires at least one `--criterion`; each gets an id (`c1`, `c2`, …). `amend --criterion`
  appends the next id and sends the need back to `contracting`.
- A new first stage, **`contracting`**, owned by proof-of-fix: done when every criterion has a probe
  recorded or a waiver. Pending, it names the criteria still open and the commands:

  ```
  repro.py record --need N --criterion c1 --cmd '<probe>' [--file tests/x.test.ts ...] [--env-aware] [--read-only]
  repro.py record --need N --criterion c1 --cmd '<probe>' ... --red-waived '<why no red run exists>'
  repro.py waive  --need N --criterion c2 --reason '<why this criterion is not behavioural>'
  ```

- **Red-first is bound to a work state.** `record` runs the probe in the current tree, dirty or not
  (the probe's own test file is usually uncommitted), and stores the work state it failed at (HEAD and
  the content hash of the changes, as `check` does today). A probe that passes is refused, unless
  `--red-waived` gives the reason; the report shows every red-waived criterion.
- **Probe files are pinned.** Every repo file the probe runs is declared with `--file`; `record`
  refuses a declared file that does not exist (so "red" never means "missing") and stores its content
  hash. `check` refuses a probe whose pinned files changed: it was edited after its red run, so it is
  recorded again, red, or red-waived with the reason (D9).
- The first criteria are recorded before `implementing` (stage order), and every first instruction says
  so: `open`'s reply and the prompt hook's nudge ask for each criterion's probe first, then the work.
  A criterion added by `amend` after the work started is recorded against the current state; if the
  need's work already makes it pass, it is red-waived with that reason.
- **Under a `delivered` contract** (Phase 3, PR 3c), contracting is done only when at least one unwaived
  criterion has a real red (not red-waived) and, when the repo deploys, at least one such criterion is
  env-aware and read-only. The conductor passes the need's end state and deploy mode to proof-of-fix's
  `stage` CLI (`--end-state`, `--deploy`), as it passes `--need` today. Otherwise the need cannot reach production with evidence of its
  own, so it stays in contracting, where the breakers bound it.

### 2.2 proof-of-fix schema v2

`.git/proof-of-fix.json` gains a `needs` map beside the v1 `sessions` map, which keeps serving the
undriven nudge and Stop flow unchanged:

```
"needs": { "<need>": { "<criterion>": {
    "cmd": "…", "files": {"<path>": "<hash>"},
    "env_aware": false, "read_only": false,
    "red":     {"head": "<sha>", "dirty": "<hash>", "rc": 1, "tail": "…"} | {"waived": "<reason>"},
    "waiver":  {"reason": "…"},
    "checked": {"head": "<sha>", "dirty": "<hash>", "rc": 0, "stable": true, "env": "local"},
    "prod":    {"sha": "<deployed sha>", "rc": 0, "at": "…"} } } }
```

- `check --need N` runs every probe of the need and writes per-criterion evidence; the tree must not
  move while it runs (as today).
- The `stage` CLI answers `contracting` and `proving` from the need's entry and the criterion ids the
  conductor passes (`--criteria`). A bug repro of a need is recorded as one of its criteria.
- Need entries are exempt from the 7-day session GC. `repro.py forget --need N` (owner command) drops
  them; the conductor calls it when a need leaves its history.

### 2.3 Env-aware probes and the local target

An env-aware probe reads `HARNESS_BASE_URL` (and `HARNESS_ENV=local|production`). Its red run must never
touch production (D7), so it needs a local target:

- Trusted config `.git/proof-of-fix.config.json` (never the cloneable tree, like every shell field):
  `{"serve": {"cmd": "…", "base_url": "http://127.0.0.1:8123", "ready_path": "/", "timeout": 60}}`.
- `record` and `check` refuse to start when something already listens on the port (it would be old
  code), start `serve` in its own process group, wait for `ready_path`, require the serve process to
  be alive when it answers, run the env-aware probes with `HARNESS_BASE_URL=base_url`, then kill the
  group by its recorded pid.
- An env-aware criterion without `serve` is refused at `record`, with the reason (D10).
- `--read-only` is the recorder's declaration that the probe only reads (D7). Phase 3 runs only
  env-aware, read-only probes against production.

### 2.4 Conductor changes

- `STAGES` starts with `contracting`; `open`'s reply and the prompt hook's nudge ask for the probes before
  the work, and the implement instruction lists each criterion with its probe.
- The proving stage passes `--need` to proof-of-fix instead of `--sessions`.
- **Report:** per-criterion evidence (probe, its pinned files or a note that it declared none, red at
  its work state or the red-waived reason, green at the shipped head, or the waiver), driven time (open to end state, blocked time excluded), and tokens
  per model, summed over the need's window from each session's transcript **and its
  `<session>/subagents/*.jsonl`** (the fresh-eyes reviewer runs there, with its own model).

### 2.5 Carried-forward fixes that fit here

- merge-review policy: define "documentation" for inline follow-ups as README, `docs/` and CHANGELOG,
  SKILL.md excluded (it is product here).
- E2E driver: treat the conductor's "ran out of hook time" continuation as a plain continue; a hermetic
  case in `tests/harness` pins `conductor_hook`'s fail-loud contract (crash, `systemMessage`,
  non-JSON, stderr).

### 2.6 Tests

- **Hermetic** (proof-of-fix and conductor suites): `open` without a criterion refused; `record`
  refuses a passing probe without `--red-waived` and a missing `--file`; a changed pinned file blocks
  proving until re-recorded; `record` on a dirty tree binds red to that work state; a waiver needs a
  reason; contracting pending, then done; amend re-enters contracting; `serve` refused on a busy port,
  started, probed and killed; adopt carries the evidence; `forget` drops a need's entries; v1 session
  entries still drive the undriven flow; the token sum includes a subagent transcript.
- **E2E `needs` space:** `need:acceptance` (a criterion red, then green at ready), `need:env-probe` (a
  static file served by `python3 -m http.server` as the local target), `need:amend` (a criterion added
  mid-need re-enters contracting). Both forges.

## Phase 4: supervisor

**Deliverable:** a need never waits on a human because its session went quiet. Two failures, two
mechanisms, and one driver per need at all times.

### 4.1 One driver per need

The binding becomes (session id, `CLAUDE_PID`, that process's start time, read as `LC_ALL=C TZ=UTC0 ps -o
lstart=`, as claude-remote-spawn does). A Stop from another process of the same session id (a human
`--resume` of a session the supervisor also resumed) stands down; SessionStart `resume` in a new
process takes the binding and stops the supervisor's `need-<id>` handle when it runs. A reused pid with
another start time is not the bound process.

A session the supervisor resumes runs inside the handle `need-<id>`: claude-remote-spawn exports
`CRS_HANDLE=<name>` into every session it launches, and the hook stops the handle only when its own
`CRS_HANDLE` differs, so a supervisor resume never stops itself. The stand-down covers every channel,
not only Stop: when the caller's session is the need's session, the prompt hook marks a pending
classification, and `change()` acts, only for the bound process (`CLAUDE_PID` is in the model's shell
too), so a second process of the same session can neither set a classification the bound one never saw
nor halt, amend or release the need. `adopt` from another session, and `--need` from a plain terminal,
keep working. The conductor's live stamp is keyed by session and pid, so the unbound process's prompt
never refreshes the bound one's.

### 4.2 An idle session (alive, nothing to wake it)

The session is alive but its background step died without a notification, or the wall-clock breaker
should fire and no Stop comes. The fix is an in-session wake-up, chosen by a measurement first (D15):

1. **Measure `asyncRewake`** on the current Claude Code: a Stop hook declared `asyncRewake` sleeps,
   exits 2, and the idle interactive session receives its text as a new turn. If it holds, the
   conductor ships a second Stop hook, `hook.py wake`, that, while the need waits, sleeps until the
   step's deadline (or the wall-clock limit) and exits 2 only if the need's `updated` did not move. One
   sleeper per need, replaced by the next Stop (tracked by pid and start time, killed by pid).
2. **Otherwise `CronCreate`:** the background-step instruction also asks for a one-shot wake-up at the
   deadline, and a `CronDelete` when the step resolves. `open` refuses when cron is disabled
   (`CLAUDE_CODE_DISABLE_CRON`).

The wake-up text is a fixed envelope, `<conductor-wakeup need="…"/>`, added to the kernel's
`MACHINE_PROMPT_RE` with `<conductor-resume need="…"/>` (4.3): a machine prompt needs no classification
and never resets the need's clock. The woken Stop re-instructs a step that died without evidence, waits
on one still running, or blocks the need on the wall clock.

### 4.3 A dead session

**`conductor.py supervise`** runs outside Claude, one pass per invocation, under a lock:

- **Registry.** `open`, `reopen`, `adopt` and `resume` register the repo in
  `~/.claude/harness-needs/registry.json` (its own directory: the live directory's 7-day GC deletes any
  file in it). A pass drops a repo only when its ledger holds no live need (active, blocked or
  abandoned), so a halted need that is resumed later stays watched.
- **Liveness** is the bound (pid, start time) pair of 4.1.
- **Resume**, for an active need whose process is dead: `driver.sh stop need-<id>` (its "no session"
  answer on a first resume counts as done; `resume` refuses a handle whose state file remains), then
  `CRS_SPAWN_CWD=<the need's worktree> driver.sh resume <session> need-<id> --in-place --prompt
  '<conductor-resume need="<id>"/>'`. claude-remote-spawn's `resume` gains `--prompt`. The SessionStart
  `resume` hook re-binds (4.1); the machine prompt starts a turn and its Stop advances the need.
- **Never a loop.** Blocked, halted and abandoned needs are never resumed; at most three resumes per
  need in 24 hours, 30 minutes apart. Past that, the need is blocked with the reason, and the pass
  raises a local desktop notification (fail-open), since only a session can send a push notification.
- **Scheduling.** `conductor.py supervisor install|uninstall|status` writes a launchd agent on macOS
  (every 5 minutes; it runs in the user's GUI session, where the login keychain is readable) or a
  systemd user timer on Linux. Opt-in (D14).

### 4.4 Tests

- **Hermetic:** supervise against the real `driver.sh` with a stubbed `claude` and fake processes: a
  dead pid is resumed with the need's session, worktree and envelope; the stubbed `claude` runs the
  SessionStart hook inside its handle and survives it; a second death is resumed again
  (the stale handle is stopped first); a live pid is left alone; a reused pid counts as dead; blocked,
  halted and abandoned needs are never resumed; a halted then resumed need stays registered; the budget
  blocks the need on the fourth death; two concurrent passes resume once; a Stop, a prompt and a CLI call
  from a second process of the bound session all stand down.
- **Turn simulator:** the wake-up path chosen in 4.2: a step dies silently, the wake-up re-instructs
  it; the wall clock blocks an idle need; the wake-up and resume envelopes skip classification.
- **Real acceptance run**, deliberate, not in CI: `tests/e2e/supervisor-acceptance.sh` spawns a real
  session in a sandbox clone with claude-remote-spawn (delivery-conductor is installed in the real
  config since 2026-09-28), opens a need, kills the Claude process during its CI wait, runs
  `supervise`, and expects the need at its end state. It costs one real session of subscription usage;
  it never uses an API key.

## Phase 3: ship-to-prod

**Deliverable:** a new plugin, `ship-to-prod`, off by default and enabled per repo (D4). With it enabled,
a need does not stop at `ready`: it is merged at its reviewed head sha on a branch up to date with its
base, its deployment is watched, and its own env-aware read-only probes run against production. Any
red after the merge opens a revert PR/MR and blocks the need (D6).

### 3.1 Policy and state

Policy `.git/ship-to-prod.json`, trusted (read through `trusted_config_paths`, never written by the
plugin):

```
{ "enabled": false,
  "deploy": "none | pipeline | command",
  "deploy_command": "…",                      # deploy: command only; runs in a worktree at the merged sha
  "verify_base_url": "https://…",
  "version_url": "https://…/version.txt",     # required unless deploy is none: answers the deployed sha
  "smoke_probes": ["curl -fsS \"$HARNESS_BASE_URL/health\""],
  "verify_timeout": 900,
  "revert_on_failure": true }
```

Merges are squash only (D4). State `.git/stp-state.json`, per need: `change_sha` (the commit that
carries the need on the base: the squash commit, or the merge commit a semi-linear forge adds),
`merged_sha` (the base tip the merge produced, what deploys; read from the forge at merge time, never
from a later fetch, which could pick up someone else's merge), the deployment verdict, the verification
verdict, the revert PR/MR.

### 3.2 The contract under ship-to-prod

`open` reads the policy once and stores the need's end state (`ready` or `delivered`) in the contract,
so a policy change never switches a need's flow midway. With `delivered`, `open` fails closed unless:

- the forge enforces up-to-date merges on the base (GitHub: branch protection or ruleset with strict
  status checks and no bypass for the merging identity, `enforce_admins` on; GitLab: `merge_method`
  `ff` or `rebase_merge`, pipelines must succeed), requires no approving review the harness cannot
  give, and has no merge queue (with one, `gh pr merge` queues or auto-merges instead of merging). A
  rule it cannot read counts as absent;
- with `deploy` other than `none`, `version_url` is set and proof-of-fix has a `serve` target (without
  one, D10 makes the env-aware criterion impossible and the need would stall in contracting). The need's own production evidence cannot be
  checked here (a criterion is text until its probe is recorded): contracting enforces it (2.1),
  `stp.py merge` checks it again, and `stp.py verify` refuses to run without a need probe;
  `smoke_probes` only add to the need's own;
- the forge CLI is authenticated with merge rights.

### 3.3 Stages after `ci`

| Stage | Owner | Done when | Next step |
|---|---|---|---|
| ready | ship-when-done | the PR/MR is not a draft | script `ship.py mark-ready` (unchanged) |
| merging | ship-to-prod | the forge reports the PR/MR merged; `change_sha` and `merged_sha` recorded | script `stp.py merge` |
| deploying | ship-to-prod | `none`: at merge. `pipeline`: the default-branch pipeline green at `merged_sha`. `command`: exited 0 | background `watch.py run --need N --sha <merged_sha> --ref <base>`, or `stp.py deploy --need N` |
| verifying | ship-to-prod | `none`: skipped, delivered at merge. Otherwise the deployed sha is `merged_sha` or descends from it, then the need's env-aware read-only probes (at least one) and every smoke probe are green against `verify_base_url` | background `stp.py verify --need N` |

`delivered` replaces `ready` as the end state and joins `NEED_CLOSED` in the kernel; the conductor
reports it and the need leaves the ledger at the next prompt, as `ready` does today. With `deploy:
none`, `delivered` means merged at the reviewed sha: the end state's production clause applies to repos
that deploy.

**Once merged, the pre-merge stages are frozen.** `stp.py merge` records their evidence in
`stp-state.json`; from then on the conductor asks only merging, deploying and verifying. Nothing can
re-open a merged need: `amend` and `reopen` are refused, and a follow-up becomes a new need that waits
until the merged one reaches its end state (the prompt hook says so, as it does today for a new need
during a need) or opens in another worktree (the PR/MR state comes from the
forge, so a need a human merged by hand is refused too).

**`stp.py merge`** (a script step, and the only irreversible one, so it trusts no cached answer):

1. If the forge already reports the PR/MR merged at the expected head sha (a merge whose state write
   was cut short), records it and stops. Otherwise it asks every earlier owner's `stage` CLI again and
   refuses unless each is done at this exact HEAD: contracting (with its `delivered` conditions) and
   proving, gate, review (score at or above threshold for this sha), CI green for this sha, PR/MR open
   and not a draft, remote head equal to HEAD.
2. Fetches the base. If the branch is behind it (base drift), it asks the forge to update the branch
   (`gh pr update-branch --rebase`; `glab mr rebase`, then waits while the MR reports
   `rebase_in_progress`), and ship-when-done's new `sync` subcommand brings the local branch to the
   forge's head (only from a clean tree whose HEAD is the old remote head). The new HEAD sends the need
   back to gating; the review is redone in full (D13). A drift that conflicts blocks the need with the
   forge's error: resolving a conflict is a human's call.
3. Merges bound to the head, never automatically: `gh pr merge <n> --squash --match-head-commit <sha>`,
   `glab mr merge <iid> --squash --sha <sha> --auto-merge=false --yes`. It then reads the PR/MR back
   from the forge and records the merge only when the forge says merged at that head. `change_sha` comes
   from the forge's own field (GitHub `mergeCommit`; GitLab `squash_commit_sha` on a fast-forward
   squash, `merge_commit_sha` otherwise). A refusal because the base moved since step 2 goes back to
   step 2; anything else blocks the need with the forge's answer.

**CI verdicts keep one owner.** This amends the 2026-09-26 ownership table (post-merge pipeline under
ship-to-prod): every CI verdict, before and after the merge, is mr-watchdog's, and ship-to-prod asks
it. mr-watchdog's `run` gains a mode that watches a sha on a ref with no PR/MR (`--sha S --ref R`),
with its verdict in its own file keyed by (ref, sha), so it never overwrites the PR verdict.
`ci_status_at` already binds a verdict to an exact sha on both forges. A ref pipeline cancelled
because a newer merge superseded it is not a red: verifying goes on, and the version gate accepts a
descendant of `merged_sha`.

**`stp.py verify`** refuses to run when the need has no env-aware read-only probe, then waits until
`version_url` answers `merged_sha` or a descendant (a fetch, then `git
merge-base --is-ancestor`), within `verify_timeout`, then runs the probes once through proof-of-fix
(`repro.py check --need N --env production`, `HARNESS_BASE_URL=verify_base_url`): a red is a red,
never an old deployment.

**`stp.py deploy`** runs `deploy_command` in a temporary worktree at `merged_sha`, never in the need's
worktree, and records its exit code and output tail.

### 3.4 Red after the merge

A red pipeline, a failed deploy command, a version that never arrives or a red production probe, with
`revert_on_failure`:

- `stp.py revert` (script step) builds the revert in a temporary worktree (the session's checkout never
  switches, so no sibling engages on it): branch `revert/<need>` from the fetched base, `git revert
  --no-edit <change_sha>` (with `-m 1` when it has two parents), push, and a PR/MR titled after the
  need with the failing evidence in its body. A revert that conflicts with later commits is aborted and
  the need blocked with the conflict; an existing `revert/<need>` that already reverts `change_sha` is
  reused;
- the need is blocked with the report (D5: the model is asked to send a push notification);
- the revert is merged by a human (D6). The revert branch is not a need.

### 3.5 Sandbox changes (both forges)

| | GitHub `harness-e2e` (public) | GitLab `harness-e2e` (private today) |
|---|---|---|
| Deploy | Pages built by a `deploy` workflow on pushes to `main` | a `pages` job on `main` |
| Steering | `deploy-plan.json` in the merged commit: `{"exit": 0, "drop": ["file"]}` (fail the deploy, or publish a site missing a file) | same |
| Version | the deploy writes `version.txt` = the deployed sha | same |
| Up to date | branch protection on `main`: status check `tests`, strict, `enforce_admins`; `allow_update_branch` on | `merge_method: ff`, squash, pipelines must succeed |
| Access | public | Pages readable anonymously (D12) |

The E2E lane plays two humans: a teammate whose own PR/MR, merged normally, moves `main` (the drift
scenario, so no bypass is ever needed), and the reviewer who merges a revert.

### 3.6 Tests

- **Hermetic** (new ship-to-prod suite, stubbed forges): merge refused on each missing piece of
  evidence and on a remote head that differs from HEAD; `--match-head-commit`, `--sha` and
  `--auto-merge=false` always passed, and a merge the forge does not confirm blocks; base drift
  updates, waits for the GitLab rebase, syncs and re-enters gating, and a conflicting drift blocks;
  `open` fails closed on an unreadable rule, a bypass, a required approval or a merge queue, and on a
  deploying repo without `version_url`; contracting under `delivered` stays pending without a real red
  or, in a deploying repo, without an unwaived env-aware read-only probe, and merge and verify refuse
  such a need; a merge interrupted after the forge merged is recorded on the next Stop; a base that
  moves between the update and the merge goes back to the update; the three deploy modes, `none`
  skipping verifying; the
  version gate accepts a descendant and waits for an older sha; revert of a single-parent and of a
  two-parent commit, built in a temporary worktree, a conflicting revert blocks; after the merge the
  conductor walks only the post-merge stages, and amend and reopen are refused; a policy change midway
  leaves the contracted end state.
- **E2E `deliver` space**, both forges: `deliver:none`, `deliver:pipeline` (Pages, version gate,
  production probe green), `deliver:deploy-red` (revert opened, merged by the E2E reviewer),
  `deliver:prod-red` (a dropped file makes the production probe red: revert), `deliver:drift` (a
  teammate PR/MR merged after our CI went green: update, re-gate, re-review, merge).

Cost: each delivered scenario runs an MR pipeline, a `main` pipeline and a Pages deployment, about 4
GitLab minutes; the space is about 40 GitLab minutes per campaign (400 per month on the free tier). On
GitHub the sandbox is public, so its minutes are free. The E2E lane scripts the model, so a campaign
costs no tokens.

## Order and working rules

Harness-core PRs land one at a time, in this order: 2a, 2b, 2c, 2d, then 4a to 4e, then 3a to 3d. A
merge on main while another core PR is open forces a rebase and a new review, which is what exhausted
the usage window in Phase 1.

Every PR: a failing test first, the repo gate, merge-review's proportionate passes (a fresh-eyes first
pass, at most two scoped confirmations, then the owner decides), version bumps in lockstep, the kernel
re-vendored when it changes. After each phase: a full `--fill` campaign on both forges, the plugins
updated in the real config (`claude plugin update`), and this plan's status updated.

## Risks

- **Review cost on drift.** Each base drift before a merge costs a full review. The report's token count
  (subagents included) shows it; D13 is revisited then.
- **Production probes are only as safe as their declaration.** Read-only is declared, not enforced
  (D7); the probes run as the user against a real URL.
- **A resumed session spends usage.** The supervisor resumes sessions without a human present; its
  budget bounds that, and it never resumes a halted or blocked need.
- **Sandbox history.** Delivered scenarios merge into the sandboxes' `main` for real; each scenario
  touches only its own files, and a revert scenario ends with its revert merged, so `main` stays
  deployable.
