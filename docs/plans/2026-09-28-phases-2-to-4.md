# Autonomous delivery, Phases 2 to 4: plan

> **Status: proposal** (2026-09-28). It continues [the autonomous-delivery plan](2026-09-26-autonomous-delivery.md)
> (D1 to D8 stand) from Phase 1 as built ([status](2026-09-27-finalize-delivery-harness.md)). Decisions
> D9 to D15 below need Benjamin's sign-off before Phase 2 starts.

**End state of the program:** in a repo that enables ship-to-prod, a need stated once goes from the prompt
to **`delivered`** (merged at its reviewed sha, deployed, verified in production by its own acceptance
probes) with no human intervention, on GitHub and on GitLab. A red deployment or a red production probe
opens a revert PR/MR and escalates. The need survives the death of its session. Elsewhere, the end state
stays `ready`.

**How the three phases get there:**

| Phase | Adds | End-to-end evidence |
|---|---|---|
| 2 | Acceptance probes: each criterion of the contract has a probe, red before the work, green at the shipped head | E2E `needs` space gains acceptance, env-aware and amended-criterion needs |
| 3 | ship-to-prod: sha-bound merge on an up-to-date branch, deployment watch, production verification, revert | E2E `deliver` space: delivered, deploy red, production red, base drift, on both forges |
| 4 | Supervisor: an idle session is woken, a dead one is resumed | hermetic supervisor suite, and one real acceptance run: a session killed mid-need, the need still reaches its end state |

---

## Starting point: Phase 1 as built

Where the build differs from the 2026-09-26 design, the build is the reference for this plan.

- **Stages** (`conductor.py STAGES`): implementing, gating, proving, reviewing, shipping, ci, ready. Each
  answer comes from the owner's read-only `stage` CLI; script steps run inside the Stop hook (120 s
  budget), background steps come back as commands carrying `--need <id>`, skill steps are judgment.
- **Criteria are free text.** `open --criterion` stores strings; nothing binds them to a probe.
  Proving checks the bug repros that the need's sessions recorded (session-keyed, schema v1).
- **Ledger:** `.git/conductor.json` with a whole-need history (20 entries) instead of the archive file;
  `need_holds()` in the kernel decides whether a need holds its branch; `reopen` restores a `ready`
  need from the history.
- **Re-entry** relies on the task notification of the background step the model launched. Neither the
  `CronCreate` wake-up nor `asyncRewake` was built, so an idle session whose step died, or a dead
  session, leaves the need waiting until someone prompts.
- **Report** at `ready`: the need, its branch and each stage's evidence; no time, no cost, no
  per-criterion evidence.

## Phase 2: acceptance probes

**Deliverable:** proving checks the contract. Every criterion of a need has a probe that failed before
the work and passes at the shipped head, or a recorded waiver saying why it is not behavioural. Probes
are keyed by need and criterion, so adopting or resuming a need carries its evidence.

### 2.1 The contract

- `open --criterion '<text>'` (repeatable) gives each criterion an id (`c1`, `c2`, …) in the ledger;
  `amend --criterion` appends the next id and sends the need back to `contracting`.
- A new first stage, **`contracting`**, owned by proof-of-fix: done when every criterion has a probe
  recorded red or a waiver. Pending, it names the criteria still open and the two commands:

  ```
  repro.py record --need N --criterion c1 [--env-aware] [--read-only] -- '<probe>'   # must fail now
  repro.py waive  --need N --criterion c2 --reason '<why this criterion is not behavioural>'
  ```

- **Red-first is bound to a tree.** `record --need` refuses a working tree with changes and stores the
  HEAD it failed at (the contract head). `contracting` runs before `implementing`, so the first
  criteria are recorded against the base. A criterion added by `amend` after the work started is
  recorded red at the current clean head; if the need's own work already makes it pass, the honest
  outcome is a waiver saying so (D9).

### 2.2 proof-of-fix schema v2

`.git/proof-of-fix.json` gains a `needs` map beside the v1 `sessions` map, which keeps serving the
undriven nudge and Stop flow unchanged:

```
"needs": { "<need>": { "<criterion>": {
    "kind": "acceptance | repro", "cmd": "…", "env_aware": false, "read_only": false,
    "red":     {"head": "<sha>", "rc": 1, "tail": "…"},
    "waiver":  {"reason": "…"},
    "checked": {"head": "<sha>", "dirty": "<hash>", "rc": 0, "stable": true, "env": "local"},
    "prod":    {"sha": "<merge sha>", "rc": 0, "at": "…"} } } }
```

- `check --need N` runs every probe of the need and writes per-criterion evidence; the tree must not
  move while it runs (as today).
- The `stage` CLI answers `contracting` and `proving` from the need's entry (`--need`), no longer from
  a list of sessions. A bug repro recorded with `--need` becomes a criterion of kind `repro`.
- Need entries are exempt from the 7-day session GC and are removed when the need leaves the history.

### 2.3 Env-aware probes and the local target

An env-aware probe reads `HARNESS_BASE_URL` (and `HARNESS_ENV=local|production`). Its red-first run
must never touch production (D7), so it needs a local target:

- Trusted config `.git/proof-of-fix.config.json` (never the cloneable tree, like every shell field):
  `{"serve": {"cmd": "…", "base_url": "http://127.0.0.1:8123", "ready_path": "/", "timeout": 60}}`.
- `record` and `check` start `serve` in its own process group, wait for `ready_path` to answer, run the
  env-aware probes with `HARNESS_BASE_URL=base_url`, then kill the group (by recorded pid, never a
  pattern).
- An env-aware criterion without `serve` is refused at `record`, with the reason (D10).
- `--read-only` is the recorder's declaration that the probe only reads (D7). Phase 3 runs only
  env-aware, read-only probes against production.

### 2.4 Conductor changes

- `STAGES` starts with `contracting`; the implement instruction lists each criterion with its probe.
- The proving stage passes `--need` to proof-of-fix instead of `--sessions`.
- **Report:** per-criterion evidence (probe, red rc at the contract head, green at the shipped head, or
  the waiver), driven time (open to end state, blocked time excluded), and token usage per model,
  summed from the assistant messages of the need's sessions within the need's window (their
  transcripts are named by session id).

### 2.5 Carried-forward fixes that fit here

- merge-review policy: define "documentation" for inline follow-ups as README, `docs/` and CHANGELOG,
  SKILL.md excluded (it is product here).
- E2E driver: treat the conductor's "ran out of hook time" continuation as a plain continue; a hermetic
  case in `tests/harness` pins `conductor_hook`'s fail-loud contract (crash, `systemMessage`,
  non-JSON, stderr).

### 2.6 Tests

- **Hermetic** (proof-of-fix suite, conductor suite): record refuses a dirty tree and a passing probe;
  a waiver needs a reason; contracting pending then done; amend re-enters contracting; `serve` started,
  probed and killed, and a `serve` that never answers fails with its output; adopt carries the
  evidence; v1 session entries still drive the undriven flow.
- **E2E `needs` space:** `need:acceptance` (a criterion red at the contract head, green at ready),
  `need:env-probe` (a static file served by `python3 -m http.server` as the local target),
  `need:amend` (a criterion added mid-need re-enters contracting). Both forges.

### 2.7 PRs

## Phase 3: ship-to-prod

**Deliverable:** a new plugin, `ship-to-prod`, off by default and enabled per repo (D4). With it
enabled, a need does not stop at `ready`: it is merged at its reviewed head sha on a branch up to date
with its base, its deployment is watched, and its env-aware read-only probes run against production.
Any red after the merge opens a revert PR/MR and blocks the need (D6).

### 3.1 Policy and state

Policy `.git/ship-to-prod.json`, trusted (read through `trusted_config_paths`, never written by the
plugin):

```
{ "enabled": false,
  "merge_method": "squash",
  "deploy": "none | pipeline | command",
  "deploy_command": "…",                      # deploy: command only
  "verify_base_url": "https://…",
  "version_url": "https://…/version.txt",     # optional: answers the deployed sha
  "smoke_probes": ["curl -fsS \"$HARNESS_BASE_URL/health\""],
  "verify_timeout": 900,
  "revert_on_failure": true }
```

State `.git/stp-state.json`, per need: merge sha, merged at, deployment verdict, verification verdict,
revert PR/MR.

### 3.2 The contract under ship-to-prod

`open` reads the policy once and stores the need's end state (`ready` or `delivered`) in the contract,
so a policy change never switches a need's flow midway. With `delivered`, `open` also checks:

- the forge enforces up-to-date merges on the base: GitHub branch protection or ruleset with strict
  status checks; GitLab `merge_method` `ff` or `rebase_merge`. Unknown (no rights to read it) fails
  closed;
- with `deploy` other than `none`, the need has an env-aware read-only criterion or the policy has
  `smoke_probes`, so every delivered need carries production evidence;
- the forge CLI can merge (authenticated, merge rights).

### 3.3 Stages after `ci`

| Stage | Owner | Done when | Next step |
|---|---|---|---|
| ready | ship-when-done | the PR/MR is not a draft | script `ship.py mark-ready` (unchanged) |
| merging | ship-to-prod | merged; `stp-state.json` holds the merge sha | script `stp.py merge` |
| deploying | ship-to-prod | `none`: at merge. `pipeline`: the default-branch pipeline green at the merge sha. `command`: the command exited 0 | background `watch.py run --need N --sha <merge> --ref <base>` or `stp.py deploy --need N` |
| verifying | ship-to-prod | every env-aware read-only probe and every smoke probe green against `verify_base_url`, at the deployed sha | background `stp.py verify --need N` |

`delivered` replaces `ready` as the end state; the conductor reports it and the need leaves the ledger
at the next prompt, as `ready` does today.

**`stp.py merge`** (a script step, and the only irreversible one, so it trusts no cached answer):

1. Asks every earlier owner's `stage` CLI again and refuses unless each is done at this exact HEAD:
   gate, proving, review (score at or above threshold for this sha), CI green for this sha, PR/MR open
   and not a draft, remote head equal to HEAD.
2. Fetches the base. If the branch is behind it (base drift), it asks the forge to update the branch
   (`gh pr update-branch --rebase`, `glab mr rebase`), and ship-when-done's new `sync` subcommand
   brings the local branch to the forge's head (only from a clean tree whose HEAD is the old remote
   head). The new HEAD sends the need back to gating; the review is redone in full (D13).
3. Merges bound to the head: `gh pr merge <n> --squash --match-head-commit <sha>`, `glab mr merge <iid>
   --squash --sha <sha> --yes`. Never auto-merge, never a local push to the base.

**CI verdicts keep one owner.** mr-watchdog's `run` gains a mode that watches a sha on a ref with no
PR/MR (`--sha S --ref R`, the default-branch pipeline after the merge); `ci_status_at` already binds a
verdict to an exact sha on both forges.

**`stp.py verify`:** when `version_url` is set, it waits until the endpoint answers the merge sha, then
runs the probes once through proof-of-fix (`repro.py check --need N --env production`, with
`HARNESS_BASE_URL=verify_base_url`), so a red is a red, never an old deployment. Without `version_url`
it re-runs the probes until green or `verify_timeout`: a propagation wait on an external system,
declared as such in the report. `version_url` is the recommended setup.

### 3.4 Red after the merge

A red pipeline, a failed deploy command or a red production probe, with `revert_on_failure`:

- `stp.py revert` (script step) builds the revert in a temporary worktree (the session's checkout never
  switches, so no sibling engages on it): branch `revert/<need>` from the fetched base, `git revert
  --no-edit <merge sha>`, push, and a PR/MR titled after the need, with the failing evidence in its
  body;
- the need is blocked with the report (D5: the model is asked to send a push notification);
- the revert is merged by a human (D6). The revert branch is not a need.

### 3.5 Conductor changes

- The stage list is chosen by the need's contracted end state.
- `reopen` asks the forge for the PR/MR state and refuses a merged or closed one: a follow-up after a
  merge opens a new need.
- The report at `delivered` adds the merge sha, the deployment and the production evidence per
  criterion.

### 3.6 Sandbox changes (both forges)

| | GitHub `harness-e2e` (public) | GitLab `harness-e2e` (private today) |
|---|---|---|
| Deploy | Pages built by a `deploy` workflow on pushes to `main` | a `pages` job on `main` |
| Steering | `deploy-plan.json` in the merged commit: `{"exit": 0, "drop": ["file"]}` (fail the deploy, or publish a site missing a file) | same |
| Version | the deploy writes `version.txt` = merge sha | same |
| Up to date | branch protection on `main`: status check `tests`, strict; `allow_update_branch` on | `merge_method: rebase_merge`, pipelines must succeed |
| Access | public | Pages access must allow anonymous reads (D12) |

The E2E lane plays two humans: a teammate who pushes to `main` (the drift scenario, through an admin
bypass kept for the sandbox) and the reviewer who merges a revert.

### 3.7 Tests

- **Hermetic** (new ship-to-prod suite, stubbed forges): merge refused on each missing piece of
  evidence and on a remote head that differs from HEAD; base drift updates, syncs and re-enters gating;
  `--match-head-commit` and `--sha` always passed; the three deploy modes; verify waits for the
  version, then runs once; revert built in a temporary worktree, never on the session's checkout; a
  policy change midway leaves the contracted end state; `open` fails closed on an unreadable forge rule.
- **E2E `deliver` space**, both forges: `deliver:none`, `deliver:pipeline` (Pages, version gate,
  production probe green), `deliver:deploy-red` (revert opened, merged by the E2E reviewer),
  `deliver:prod-red` (a dropped file makes the production probe red: revert), `deliver:drift` (a
  teammate commit on `main` after CI green: update, re-gate, re-review, merge).

Cost: each delivered scenario runs an MR pipeline, a `main` pipeline and a Pages deployment, about 4
GitLab minutes; the space is about 40 GitLab minutes per campaign (400 per month on the free tier). On
GitHub the sandbox is public, so its minutes are free.

### 3.8 PRs

|---|---|---|
| 3a | mr-watchdog `run --sha --ref` (a ref without a PR/MR); ship-when-done `sync` | both suites |
| 3b | ship-to-prod plugin: policy, `open` checks, `merge`, `deploy`, `verify`, `revert`, `stage` CLI | its suite |
| 3c | conductor: end state by contract, the three stages, `reopen` asks the forge, delivered report | conductor suite, turn simulator |
| 3d | sandbox changes on both forges (a separate commit in each sandbox repo), E2E `deliver` space, `--fill` | ledger fresh on both forges |

## Phase 4: supervisor

**Deliverable:** a need never waits on a human because its session went quiet. Two different failures,
two mechanisms.

### 4.1 An idle session (alive, nothing to wake it)

The session is alive but its background step died without a notification, or the wall-clock breaker
should fire and no Stop comes. The fix is an in-session wake-up; which mechanism is decided by a
measurement first (D15):

1. **Measure `asyncRewake`** on the current Claude Code: a Stop hook declared `asyncRewake` sleeps,
   exits 2, and the idle interactive session receives its text as a new turn. If it holds, the
   conductor ships a second Stop hook, `hook.py wake`, that, while the need waits, sleeps until the
   step's deadline (or the wall-clock limit) and exits 2 only if the need's `updated` did not move. One
   sleeper per need, replaced by the next Stop (tracked by pid and start time, killed by pid).
2. **Otherwise `CronCreate`:** the background-step instruction also asks for a one-shot wake-up at the
   deadline, with a fixed machine envelope (`<conductor-wakeup need="…"/>`) that
   `is_machine_prompt` classifies as machine, and a `CronDelete` when the step resolves. `open`
   refuses when cron is disabled (`CLAUDE_CODE_DISABLE_CRON`).

Either way, the woken Stop re-instructs a step that died without evidence, waits on one still running,
or blocks the need on the wall clock.

### 4.2 A dead session

**`conductor.py supervise`** runs outside Claude, one pass per invocation:

- **Registry.** `open`, `reopen` and `adopt` register the repo in `~/.claude/harness-needs/registry.json`
  (its own directory: the live directory's 7-day GC deletes any file in it); a pass drops repos whose
  ledger holds no active need.
- **Liveness.** A need's session is alive when its `CLAUDE_PID` runs with the process start time
  recorded at binding (`LC_ALL=C TZ=UTC0 ps -o lstart=`, as claude-remote-spawn does), so a reused pid
  is not a live session. The conductor records the start time wherever it records the pid.
- **Resume.** For an active need whose session is dead: `CRS_SPAWN_CWD=<worktree>
  driver.sh resume <session> need-<id> --in-place --prompt '<conductor-resume need="<id>"/>'`.
  claude-remote-spawn's `resume` gains `--prompt`. The SessionStart `resume` hook re-binds the pid (built
  in Phase 1); the machine prompt starts a turn and its Stop advances the need.
- **Never two drivers, never a loop.** One pass at a time (a lock); a need is resumed only if its
  session is dead; blocked, halted and abandoned needs are never resumed; at most three resumes per
  need in 24 hours, 30 minutes apart. Past that, the need is blocked with the reason, and the pass
  raises a local desktop notification (fail-open) since only a session can send a push notification.
- **Scheduling.** `conductor.py supervisor install|uninstall|status` writes a launchd agent on macOS
  (every 5 minutes; it runs in the user's GUI session, where the login keychain is readable) or a
  systemd user timer on Linux. Opt-in (D14).

### 4.3 Tests

- **Hermetic:** supervise with a stubbed `driver.sh` and fake processes: a dead pid is resumed with the
  need's session, worktree and envelope; a live pid is left alone; a reused pid (same pid, other start
  time) counts as dead; a blocked or halted need is never resumed; the budget blocks the need on the
  fourth death; two concurrent passes resume once; the registry drops finished repos.
- **Turn simulator:** the wake-up path chosen in 4.1: a step dies silently, the wake-up re-instructs
  it; the wall clock blocks an idle need.
- **Real acceptance run**, deliberate, not in CI: `tests/e2e/supervisor-acceptance.sh` spawns a real
  session in a sandbox clone with claude-remote-spawn, opens a need, kills the Claude process during
  its CI wait, runs `supervise`, and expects the need at its end state. It costs one real session of
  subscription usage; it never uses an API key.

## Order and dependencies

1. **Phase 2** first: Phase 3's production verification runs Phase 2's probes. 2a, then 2b and 2c,
   then 2d.
2. **Phase 3:** 3a, then 3b and 3c, then 3d. The sandbox changes of 3d wait for D12.
3. **Phase 4** can start after 2b (it needs the ledger fields, not ship-to-prod): 4a and 4b in
   parallel with Phase 3, but never two harness-core PRs open at once (the working rule of Phase 1).
4. After each phase: a full `--fill` campaign on both forges, and the plan's status section updated.

Every PR: a failing test first, the repo gate, merge-review's proportionate passes (a fresh-eyes first
pass, at most two scoped confirmations, then the owner decides), version bumps in lockstep, and the
kernel re-vendored when it changes.

## Risks

- **Review cost on drift.** Each base drift before a merge costs a full review. In repos with frequent
  merges this could dominate; the report's token count will show it, and D13 is revisited then.
- **Production probes are only as safe as their declaration.** Read-only is declared, not enforced
  (D7). The policy's `smoke_probes` and the need's own probes run as the user against a real URL.
- **Pages propagation.** Without `version_url`, verification waits on an external system with a
  timeout. The sandbox uses `version_url` so its reds are real.
- **A resumed session spends usage.** The supervisor resumes sessions without a human present; its
  budget bounds that, and it never resumes a halted or blocked need.
- **Sandbox history.** Delivered scenarios merge into the sandboxes' `main` for real; each scenario
  touches only its own files, and a revert scenario ends with its revert merged, so `main` stays
  deployable.
